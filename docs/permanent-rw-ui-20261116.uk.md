# Постійний Evolution X 16 RW та пароль перед форматуванням

Перевірена збірка: **1.1.0-dev-evox-rw-ui1**, Samsung SM-A226B, ядро #145.
Завершення перевірки: 2026-11-17 (Europe/Berlin).

## Реалізована поведінка

Для кваліфікованого поточного профілю Evolution X 16 з паролем доступні читання
та запис userdata. За замовчуванням пропонується читання. У Files потрібно вибрати
userdata, потім «Змонтувати для читання» або «Змонтувати із записом» до введення
пароля Android. Можливість RW перевіряється повторно після визначення фактичного
профілю й типу облікових даних.

Інтерфейс показує фактичний режим монтування. Повторний запит того самого режиму
повертає поточну сесію без нової автентифікації. Для зміни RO/RW потрібно штатно
відмонтувати дані та перезапустити recovery: поточний TEE lifecycle допускає одну
сесію перевірки облікових даних на запуск. Обмеження не обходиться повторними спробами.

Відомий busy-стан зберігає сесію та має окреме пояснення. Після невизначеного
результату інтерфейс перечитує фактичний стан, без автоматичного повторення
автентифікації. Очікувані перезапуск, зайнятість, зміна стану та завершення строку
підтвердження мають зрозумілі повідомлення; технічні коди лишаються у журналі.

## Форматування

Штатні Files → форматування userdata та Wipe → Data for Android вимагають нової
native-перевірки поточного пароля/PIN Android. Самого вже відкритого розділу
недостатньо. Починати цю дію треба на свіжому запуску recovery, перед звичайним
розблокуванням даних.

Пароль передається через захищений файловий дескриптор. Після успішної перевірки
дані відкриті лише для читання, а користувач бачить окреме підтвердження:
утримання кнопки форматування 5 секунд. Одноразовий дозвіл діє 120 секунд і
прив'язаний до поточного boot, фізичного userdata, сесії, політики шифрування,
цільової файлової системи та операції.

Скасування, вихід зі сторінки, блокування й завершення строку забирають можливість
підтвердження. Backend перевіряє дозвіл і штатне закриття сесії до запуску запису.
Інсталяційні шляхи, які могли б очистити захищений userdata, також зупиняються
перед записом без потрібної підготовки. Cache очищається після успішного reset
даних; часткова помилка не пропонує повторно стирати вже скинуті дані.

| Рівень | Результат |
|---|---|
| Python backend | 317 тестів PASS; включно з двома actual-base guards без пропусків |
| UI | 106 self-tests, профільні unlock/format сценарії, 3 Files workflows PASS |
| Українські повідомлення | 2323/2323; екрани RO/RW, пароль, підтвердження та очікувані стани переглянуті |

| Встановлення | Резервна копія попереднього RECOVERY та повне незалежне читання нового; BOOT незмінний |
| Password RW на телефоні | Штатна Files authentication, фактичний RW, native CE/policy proof PASS |
| Файлові дії на телефоні | Власні 64 КіБ: create/fsync, повне читання, rename/fsync, повне читання, delete/dirfsync; 14 Files API викликів |
| Режими на телефоні | Повторний RW без authentication; протилежний RO відхилено зі збереженням поточного RW |
| Пароль перед форматуванням | На іншому boot: свіжа перевірка, валідний дозвіл, cancel, повторна validation відхилена |
| Після перезапуску | Обидві назви тестового файла відсутні на тому самому userdata і з тією самою fscrypt policy |
| Завершення | Обидві сесії нормально закриті; незалежно перевірені DM/mount/process cleanup та EFS clean; фінальний fresh idle boot |

Поточний native RW спирається також на раніше закритий фізичний цикл 4 MiB:
write/fsync → новий boot/read/hash → delete/fsync → новий RO boot/absence.
Новий 64 KiB тест перевіряє інтегровані Files операції та збереження видалення
після перезапуску; ці два набори доказів не підміняють один одного.

## Межі перевірки

- RW кваліфікований для поточного exact Evolution X 16 password-профілю; це не
  універсальна кваліфікація інших ROM, NONE або pattern.
- Реальне стирання userdata/reset у цій перевірці не запускалося. На телефоні
  перевірені пароль, видача/відкликання дозволу й відмова після скасування;
  destructive writer, неправильний пароль, expiry, busy та відмови cleanup
  перевірені у відповідних офлайн-сценаріях.
- Апаратну зайнятість розділу навмисно не провокували.
- UI перевірений через виконання його коду, fixtures і зображення екранів.
  На телефоні підтверджені встановлений ARM64 binary та живий UI process;
  автоматизований фізичний touchscreen walkthrough не заявляється.
- Окремий повний Android app/system backup/restore цим етапом не кваліфіковано.
